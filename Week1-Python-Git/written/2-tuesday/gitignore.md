# .gitignore

## Learning Objectives

By the end of this lesson you will be able to:

- Explain what a `.gitignore` file is and why every repository needs one.
- Identify the kinds of files that should never be committed.
- Create a `.gitignore` file and write patterns using `*`, `?`, `/`, `**`, `!` and `#`.
- Build a sensible `.gitignore` for a Python project.
- Verify that Git is ignoring (or not ignoring) a file with `git status` and `git check-ignore`.
- Stop tracking a file that was committed by mistake using `git rm --cached`.
- Explain why committing secrets is dangerous and how `.gitignore` helps (and where it does not).

---

## Why This Matters

On Monday you learned `git add .`, which stages **everything** in the folder. That is convenient, and dangerous. Real projects accumulate files that don't belong in version control:

- **Generated files**, such as Python's `__pycache__` folders, which Python recreates automatically.
- **Personal or machine-specific files**, such as editor settings or operating-system clutter (`.DS_Store`, `Thumbs.db`).
- **Large or temporary files**, such as logs, downloaded data and test reports.
- **Secrets**, such as passwords, API keys, tokens and `.env` files.

Committing these causes real problems. Generated files create noisy history and constant merge conflicts between teammates. Large files bloat the repository. And **secrets committed to a shared repository are a serious security incident**; once pushed, they can be copied by anyone with access, and removing them from history is difficult.

In test automation specifically, projects produce test reports, screenshots, log files, browser drivers and credentials files for test environments. A good `.gitignore` is one of the first things set up in any automation repository. Today's exercise asks you to include a `.gitignore` in your project and push it, so this is a hands-on skill.

## The Concept

### 1. What Is `.gitignore`?

A **`.gitignore`** file is a plain text file, placed in your repository, that lists **patterns of files and folders Git should ignore**. Ignored files:

- do not appear as untracked in `git status`,
- are skipped by `git add .`,
- never get committed accidentally.

**Analogy:** think of a "do not pack" list for a suitcase. Before you leave, you check the list, so you don't pack the dirty laundry, even if it's lying right next to the suitcase.

A few facts to remember:

- The file name is exactly `.gitignore`: starting with a dot, no extension.
- It normally lives in the **root** of your repository (the same folder that contains `.git`).
- The `.gitignore` file itself **should be committed**, so that everyone who clones the project gets the same rules.
- It only affects **untracked** files. If a file is already tracked (committed), adding it to `.gitignore` doesn't stop Git tracking it (we'll fix that in section 7).

---

### 2. What Should Be Ignored?

| Category | Examples | Why |
|---|---|---|
| Python generated files | `__pycache__/`, `*.pyc` | Recreated automatically; differ per machine |
| Virtual environments | `.venv/`, `venv/`, `env/` | Large; rebuilt from a requirements list |
| Secrets & config | `.env`, `secrets.json`, `*.pem`, `credentials.*` | Security |
| Editor / IDE settings | `.idea/`, `*.swp`, sometimes `.vscode/` | Personal preferences |
| OS files | `.DS_Store`, `Thumbs.db` | Meaningless clutter |
| Logs and temp files | `*.log`, `tmp/` | Generated at runtime |
| Test output | `reports/`, `screenshots/`, `.pytest_cache/`, `htmlcov/` | Generated by test runs |
| Build/dist output | `build/`, `dist/`, `*.egg-info/` | Generated |
| Large data | `*.csv` (if huge), `*.zip` | Bloats the repo |

**What should NOT be ignored:** your source code, tests, README, configuration that everyone needs (e.g. `requirements.txt`), and the `.gitignore` itself.

---

### 3. Creating a `.gitignore`

Create the file in the root of your repository using VS Code (New File, name it `.gitignore`) or the terminal:

```bash
touch .gitignore        # macOS / Linux / Git Bash
```

Open it and type one pattern per line. Here is a first example:

```gitignore
# Python cache files
__pycache__/
*.pyc

# Secrets
.env

# Logs
*.log
```

Explaining each line:

- Lines starting with `#` are **comments**; Git ignores them. Use them to explain groups of rules.
- `__pycache__/` ignores any folder named `__pycache__`. A trailing slash means "this is a directory".
- `*.pyc` ignores any file ending with `.pyc`.
- `.env` ignores a file named `.env`.
- `*.log` ignores every file ending with `.log`.
- Blank lines are ignored; use them to group sections.

---

### 4. Pattern Syntax in Detail

| Pattern | Meaning | Example matches |
|---|---|---|
| `file.txt` | A file with this exact name, anywhere in the repo | `file.txt`, `docs/file.txt` |
| `*.log` | `*` matches any number of characters (not `/`) | `app.log`, `logs/error.log` |
| `?` | Exactly one character | `file?.txt` matches `file1.txt`, not `file10.txt` |
| `[abc]` | One character from the set | `file[12].txt` matches `file1.txt` and `file2.txt` |
| `folder/` | A directory (and everything in it) | `folder/`, `a/folder/` |
| `/folder` | Leading `/` anchors to the repo root only | `/build` matches only top-level `build` |
| `docs/*.pdf` | A path pattern: PDFs directly inside `docs` | `docs/a.pdf`, not `docs/x/a.pdf` |
| `**/temp` | `**` matches nested directories | `temp`, `a/temp`, `a/b/temp` |
| `docs/**/*.pdf` | PDFs anywhere below `docs` | `docs/a/b/c.pdf` |
| `!important.log` | **Negation**: do *not* ignore this | Re-includes `important.log` |
| `# text` | Comment | Not a pattern |

#### Examples with explanation

```gitignore
# Ignore every .log file
*.log

# ...but keep this one
!keep-this.log

# Ignore the build folder at the top level only
/build/

# Ignore any folder named reports anywhere
reports/

# Ignore all .txt files in the notes folder only
notes/*.txt
```

#### Negation rules and a common trap

Rules are processed top to bottom; later rules can override earlier ones. But you **cannot re-include a file if its parent folder is ignored**:

```gitignore
logs/
!logs/important.log     # does NOT work: the whole logs/ folder is excluded
```

To make it work, ignore the *contents* instead of the folder:

```gitignore
logs/*
!logs/important.log
```

#### Matching is case-sensitive on some systems

Write patterns with the exact case of your file names, to be safe on Linux build servers.

### 5. A Practical `.gitignore` for a Python Project

Here is a reasonable starter file for the Python and test-automation work in this program:

```gitignore
# ---------- Python ----------
__pycache__/
*.py[cod]
*.egg-info/
build/
dist/

# ---------- Virtual environments ----------
.venv/
venv/
env/

# ---------- Secrets and local config ----------
.env
*.pem
secrets.json

# ---------- Test output ----------
.pytest_cache/
htmlcov/
.coverage
reports/
screenshots/
*.log

# ---------- Editors ----------
.vscode/
.idea/
*.swp

# ---------- Operating system ----------
.DS_Store
Thumbs.db
```

Note `*.py[cod]` matches `.pyc`, `.pyo` and `.pyd`, using a character set.

> **Teams differ on `.vscode/`.** Some teams commit shared editor settings, so they don't ignore it. Follow your team's convention.

**Don't write from scratch every time.** GitHub offers ready-made templates: when you create a repository on GitHub you can choose **Add .gitignore → Python**. The repository https://github.com/github/gitignore also contains templates for dozens of languages and tools. Start from a template and add project-specific entries.

### 6. Seeing It Work

Set up a quick experiment in a practice repository:

```bash
mkdir ignore-demo
cd ignore-demo
git init
```

Create these files (any content): `app.py`, `debug.log`, `.env`, and a folder `__pycache__/` containing `app.cpython-312.pyc`. Run:

```bash
git status
```

```text
Untracked files:
        .env
        __pycache__/
        app.py
        debug.log
```

Everything shows up. Now create `.gitignore`:

```gitignore
__pycache__/
*.log
.env
```

and run `git status` again:

```text
Untracked files:
        .gitignore
        app.py
```

The ignored files have vanished from the list. Notice that `.gitignore` itself appears as untracked: you should commit it.

```bash
git add .gitignore app.py
git commit -m "Add app script and .gitignore"
```

#### Checking why a file is ignored

When a file isn't showing up and you aren't sure why:

```bash
git check-ignore -v debug.log
```

```text
.gitignore:2:*.log      debug.log
```

This tells you the rule (`*.log`, on line 2 of `.gitignore`) responsible. If the command prints nothing, the file is **not** ignored.

To list all ignored files in the project:

```bash
git status --ignored
```

### 7. When the File Is Already Tracked

`.gitignore` only prevents Git from *starting* to track a file. If you committed `debug.log` before adding `*.log` to `.gitignore`, Git will continue to track it and show its changes.

To make Git **stop tracking** the file, but keep it on your disk:

```bash
git rm --cached debug.log
```

- `git rm` normally removes a file from Git **and** from your disk.
- `--cached` limits the removal to Git's index, leaving your file untouched.

Then commit the change:

```bash
git commit -m "Stop tracking debug.log"
```

For a whole folder, add `-r` (recursive):

```bash
git rm -r --cached __pycache__
git commit -m "Stop tracking Python cache files"
```

After this, the file is untracked and ignored. **Important:** the file remains in the repository's earlier history. For ordinary files, that's fine. For **secrets**, see below.

### 8. Secrets: A Special Warning

If you accidentally commit a password or API key:

1. Adding it to `.gitignore` afterwards **does not remove it from history**.
2. If you've pushed to a remote like GitHub, treat the secret as **compromised**: automated scanners look for exposed keys within minutes.
3. The correct response is to **revoke or rotate the secret immediately** (generate a new password or key), and then, if needed, clean history with specialized tools (advanced; your team's security guidelines will say how).

The best defense is prevention:

- Set up `.gitignore` **before** your first commit.
- Keep secrets in a `.env` file (ignored) and commit a safe template named `.env.example` containing placeholder values, such as `API_KEY=your-key-here`, so teammates know which settings are needed.
- Run `git status` and read it before every commit.

### 9. Ignoring Files Just for You

Sometimes you want to ignore files only on your own machine, without touching the shared `.gitignore`:

- **`.git/info/exclude`**: works like `.gitignore` but is local to your clone and is not committed.
- **A global ignore file**: rules that apply to *all* your repositories (good for OS or editor clutter):

```bash
git config --global core.excludesfile ~/.gitignore_global
```

Then put entries like `.DS_Store` and `Thumbs.db` in `~/.gitignore_global`.

---

### 10. Keeping an Empty Folder

Git tracks **files**, not folders, so an empty folder can't be committed. A common convention is to put an empty placeholder file, usually named `.gitkeep`, inside:

```text
reports/
└── .gitkeep
```

To keep the folder but ignore everything else in it:

```gitignore
reports/*
!reports/.gitkeep
```

### 11. Common Mistakes

| Mistake | Result | Fix |
|---|---|---|
| Naming the file `gitignore` or `.gitignore.txt` | Rules have no effect | Name it exactly `.gitignore` (watch for hidden file extensions on Windows) |
| Adding a rule after the file is already tracked | File still tracked | `git rm --cached <file>` and commit |
| Not committing `.gitignore` | Teammates don't get the rules | Commit it |
| Trailing spaces or wrong slashes (`\`) | Pattern doesn't match | Use forward slashes `/`, no trailing spaces |
| Ignoring everything with `*` by accident | Nothing is tracked | Review patterns; use `git status --ignored` |
| Un-ignoring a file inside an ignored folder | Negation fails | Ignore the contents with `folder/*` instead |
| Committing secrets "just once" | Permanent exposure risk | Rotate the secret; prevent next time |
| Creating `.gitignore` in a subfolder by mistake | Rules apply only to that subfolder | Place it in the repo root |

## Summary

- A **`.gitignore`** file tells Git which files and folders to ignore: generated files, secrets, logs, editor and OS clutter, large or temporary data.
- It lives in the repository root and **should be committed**. It applies only to **untracked** files.
- Patterns: `*` (any characters), `?` (one character), `[abc]` (a set), `folder/` (a directory), `/name` (root only), `**` (any depth), `!` (negation), `#` (comment).
- Set up `.gitignore` **before the first commit**; start from a template such as GitHub's Python one.
- Check with `git status`, `git status --ignored` and `git check-ignore -v <file>`.
- Already tracked? Use `git rm --cached <file>` (then commit) to stop tracking without deleting the file.
- **Never commit secrets.** If it happens, rotate the secret. Keep `.env` ignored and share a `.env.example` instead.
